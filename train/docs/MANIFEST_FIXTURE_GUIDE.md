# Manifest Fixture and Validator Guide

Status: learning note plus implementation guide, 2026-06-20.

This guide explains what the Phase 1 manifest fixtures are, what the new
validator checks, and how this relates to real SFT/GRPO training data.

## Short Version

We now have three layers:

```text
1. Contract
   Human-readable task intent: ports, behavior, properties, forbidden constructs.

2. Manifest
   Machine-readable evidence ledger: IDs, hashes, verifier reports, split, use flags.

3. Training JSONL / Parquet
   Model-visible examples generated by packers from admitted manifests.
```

The validator checks layer 2. It does not train a model and it does not prove
simulator correctness.

## Why This Exists

Without manifests, every downstream script is tempted to invent its own answer
to these questions:

- Which candidate is this?
- Which contract generated it?
- Did EVAS compile and simulate it?
- Was it checked against protected vaBench release assets?
- Was it Spectre-shadow audited?
- Which split owns it?
- Can it be used for SFT gold?
- Can it be used as a GRPO prompt?
- Which reward profile should GRPO use?

That is dangerous because SFT, GRPO, contamination checking, and evaluation can
silently disagree. The manifest layer forces one shared source of truth.

## Concrete Toy Example

The current fixture has one candidate:

```text
candidate_id: cand_toy_l1_hysteresis_comparator_dut_0001
contract_id: cg_l1_hysteresis_comparator_dut_0001
item_id: adm_toy_l1_hysteresis_comparator_dut_0001
split_key: comparator/hysteresis_toy_fixture
```

Its flow is:

```text
candidate_index
  says: "this generated candidate exists and points to this contract/artifacts"

static_check_report
  says: "cheap structural checks passed"

evas_verification_report
  says: "EVAS Rust parser/elaboration, sim health, and properties passed"

contamination_report
  says: "no protected release overlap was detected"

spectre_shadow_report
  says: "toy EVAS/Spectre agreement shape is present"

diversity_report
  says: "not rejected as a template duplicate"

split_manifest
  says: "this admitted item is assigned to SFT/GRPO fixture splits"

admitted_manifest
  says: "packers are allowed to consume this item"

sft_pack_manifest / grpo_prompt_manifest
  say: "this is how downstream training files should be produced"
```

Only `admitted_manifest` should be consumed by SFT/GRPO packers. Raw generated
candidates are not enough.

## Example: Candidate vs Admitted Item

Candidate-level record:

```yaml
candidate_id: cand_toy_l1_hysteresis_comparator_dut_0001
contract_id: cg_l1_hysteresis_comparator_dut_0001
state: evas_verified
artifact_hashes:
  dut_va: sha256:dddd...
reward_profile: L1_dut
intended_uses:
  sft_gold: true
  grpo_prompt: true
```

This says the candidate exists and may be intended for SFT/GRPO, but intention is
not admission.

Admitted-level record:

```yaml
item_id: adm_toy_l1_hysteresis_comparator_dut_0001
candidate_id: cand_toy_l1_hysteresis_comparator_dut_0001
evidence_refs:
  evas: data/manifests/examples/evas_verification_report.synth-batch-toy-0001.yaml
  contamination: data/manifests/examples/contamination_report.synth-batch-toy-0001.yaml
use_flags:
  sft_gold: true
  grpo_prompt: true
pack_targets:
  - sft_train
  - grpo_train
```

This says the evidence chain passed and packers may consume the item.

## Example: Why GRPO Prompt Must Not Include Gold Completion

SFT learns by imitating a target answer:

```json
{
  "instruction": "Write a Verilog-A hysteresis comparator.",
  "input": "Ports: inp, inn, out. Behavior: ...",
  "output": "<think>...</think><answer>module ... endmodule</answer>"
}
```

GRPO learns by sampling completions and scoring them:

```json
{
  "item_id": "adm_toy_l1_hysteresis_comparator_dut_0001",
  "prompt": "Write a Verilog-A hysteresis comparator. Ports: inp, inn, out. Behavior: ...",
  "contract_ref": "data/contracts/examples/l1_hysteresis_comparator_dut.yaml",
  "reward_profile": "L1_dut"
}
```

The GRPO prompt must not include:

```text
output
completion
gold_completion
answer
```

If it did, the policy could copy the answer instead of learning from reward.

## What Pydantic Adds

YAML only checks syntax. This is valid YAML:

```yaml
candidate_id: 123
reward_profile: []
```

But it is not a valid candidate manifest. Pydantic adds type and field checks:

- `candidate_id` must be a string;
- `level` must be `L0`, `L1`, or `L2`;
- required fields must exist;
- unknown fields are rejected in the current fixture models;
- GRPO prompt manifests must list completion fields as forbidden;
- EVAS compile status must explicitly mean EVAS Rust parser/elaboration.

## What the Validator Checks

Run:

```bash
python3 -m train.pipelines.validate_manifest_fixtures
```

The validator checks:

1. all 13 YAML fixture files parse;
2. each file has the expected top-level fields;
3. SHA-like fields use `sha256:<64 lowercase hex chars>`;
4. all reports reference the same `candidate_index_hash`;
5. contamination report references the protected index hash;
6. Spectre shadow manifest references the EVAS report hash;
7. admitted manifest source hashes match the report hashes;
8. SFT and GRPO pack manifests reference only admitted item IDs;
9. candidate hashes do not reuse protected hashes;
10. GRPO prompt fields forbid `output`, `completion`, `gold_completion`, and
    `answer`;
11. local manifest references point to existing fixture or contract files.

Expected output:

```text
manifest_fixture_validation_ok=1
examples_dir=train/data/manifests/examples
candidate_count=1
admitted_count=1
candidate_ids=cand_toy_l1_hysteresis_comparator_dut_0001
admitted_item_ids=adm_toy_l1_hysteresis_comparator_dut_0001
```

## What the Validator Does Not Check Yet

It does not:

- run EVAS;
- run Spectre;
- compute real file hashes;
- perform real contamination similarity matching;
- generate SFT JSONL;
- generate GRPO prompt files;
- prove that the remote server environment is healthy.

Those are later pipeline stages. The current validator only proves that the
manifest interface is mechanically coherent.

## Mental Model

Use this analogy:

```text
Contract = exam question specification
Candidate = a proposed answer package
Verifier reports = grading sheets
Admitted manifest = registrar-approved transcript
SFT JSONL = worked solution shown to the student
GRPO prompt = exam question without answer, graded by verifier reward
```

The validator checks that the transcript and grading sheets refer to the same
student, question, and evidence.

## Current Implementation Status

The fixture validator has now been split into reusable schema and local pipeline
tools:

```text
train/pipelines/manifest_schemas.py
train/pipelines/build_protected_index.py
train/pipelines/check_contamination.py
train/pipelines/pack_sft.py
train/pipelines/pack_grpo.py
```

The closed-loop relationship is documented in
`PHASE1_CLOSED_LOOP_PIPELINES.md`. Do not start bulk LLM synthesis before the
protected index and contamination checker are run against the actual protected
vaBench release assets.
